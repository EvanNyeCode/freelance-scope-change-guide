# Freelance technical-writer scope-change guide

Technical-writing projects often change after the first brief: a new API version appears, a subject-matter expert adds requirements, examples need verification, or a review round expands into a rewrite. The useful boundary is to make the added work, price, and schedule visible before starting it.

This guide is planning help for freelance technical writers, documentation consultants, and small documentation teams. It is not a contract or legal advice.

## Start with the approved scope

Before pricing a new request, keep the original agreement visible:

- documentation deliverables and formats;
- audience, product version, and publication destination;
- source access, subject-matter-expert availability, and client inputs;
- research, writing, example, screenshot, and review assumptions;
- included review rounds and acceptance criteria;
- delivery milestones and dependencies; and
- exclusions such as migration, translation, maintenance, support, or extra formats.

A request can be reasonable and still change the agreed deliverable, assumptions, review allowance, or deadline.

## Common technical-writing scope changes

Examples include:

- documenting an additional endpoint, feature, or product version;
- adding tutorials, troubleshooting content, or alternate audience versions;
- verifying new code samples or reproducing a workflow;
- adding screenshots, diagrams, video scripts, or localization-ready variants;
- coordinating another subject-matter-expert review round;
- rewriting approved content because the product or requirements changed; or
- moving a publication deadline before the required source material is ready.

Name the specific change instead of describing it as “a little more documentation.”

## Estimate the added work

Break the request into the work it actually adds:

1. source review and access coordination;
2. outline, research, and information architecture;
3. drafting or rewriting;
4. example, code, or workflow verification;
5. review coordination and revision time; and
6. formatting, publishing, and handoff.

Apply the rate that fits the project and agreement. Add coordination, uncertainty, or rush impact only when it is real and explainable.

`added price = added hours × project rate + justified real adjustment`

State the schedule effect next to the price. If access, product readiness, or SME feedback is uncertain, describe the dependency rather than hiding it inside an arbitrary buffer.

## Copy-ready client response

> Thanks for the request. The [new endpoint/tutorial/version/review round] sits outside the current documentation scope because [deliverable, input, revision, or deadline difference]. I can add it for [price], with delivery moving to [date or milestone] after [required input]. Or we can keep the approved documentation scope and schedule this as a follow-on phase. Please confirm which option you prefer before I begin the added work.

Adapt the wording to the actual agreement and avoid calling a defect correction a new scope change when it is covered by the acceptance criteria.

## What to record

Keep a short change record containing:

- the original documentation deliverable;
- the requested addition and affected audience or version;
- source, access, and subject-matter-expert assumptions;
- added hours and rate basis;
- price and any real adjustment;
- revised milestone or publication date;
- included review or revision limit; and
- written approval before the new work starts.

If the request changes again, compare it with the approved change rather than silently absorbing it into the original quote.

## Final check before starting

- Is the new documentation output named?
- Are source and client-input dependencies explicit?
- Is the added effort tied to a clear price?
- Is the schedule impact visible?
- Are review and acceptance limits stated?
- Is written approval recorded?
